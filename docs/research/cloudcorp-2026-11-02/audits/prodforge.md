# Security Audit — prodforge

- **Repo:** github.com/CloudCorpRecords/prodforge (MIT)
- **Version:** 0.5.0 (`package.json`, also `VERSION` in `src/cli.ts`)
- **npm:** `@reneturcios/prodforge` · **Bin:** `prodforge` → `dist/cli.js`
- **Dependencies:** runtime `@modelcontextprotocol/sdk ^1`, `zod ^3`; dev `@types/node ^20`, `tsx ^4`, `typescript ^5`
- **Method used:** `git clone` is broken VM-wide (“unable to write symref for HEAD: Operation not permitted”) and codeload tarballs return 0 bytes through the proxy, and tar extraction into the scratch tree hit write-EPERM — so no local `src/` copy could be persisted. Primary method per coordinator: `gh api repos/CloudCorpRecords/prodforge/git/trees/main?recursive=1` for the file inventory and `gh api repos/CloudCorpRecords/prodforge/contents/<path>` (base64 content) for source, cross-checked with streamed `raw.githubusercontent.com` reads: full-file reads of `package.json` and every `src/*.ts`, and `grep -n` scans of the remaining files listed under Coverage. Nothing was installed or run.
- **Coverage:** All executable source covered — `package.json`, every file in `src/` (`catalog.ts`, `cli.ts`, `doctor.ts`, `index.ts`, `mcp.ts`, `scaffolds.ts`, `ship.ts`), plus `test/*.ts`, `examples/notes/src/index.ts`, `examples/taskboard/src/index.ts` + example `package.json`s, `catalog/registry.json`, `catalog/mcp-servers.json` (registry inventoried/scanned), `mcp/mcp.json`, `Dockerfile`, `server.json`, workflows. `docs/`, `playbooks/`, `stacks/` are markdown (inventoried, not code).

## Findings

- **Install hooks:** Scripts are `build`, `dev`, `test` only. **No** `preinstall` / `postinstall` / `prepare`.
- **Network egress: none in prodforge's own code.** Grep across all of `src/` finds no `fetch`, no `http/https/net/tls` imports, no WebSocket, no hardcoded URLs. The catalog is **bundled local JSON**, read from disk (`src/catalog.ts` `loadCatalog()` / `loadMcpServers()` via `readFileSync` of `catalog/registry.json` / `catalog/mcp-servers.json`). Catalog data itself lists 27 fleet tools — every `repo` is `https://github.com/CloudCorpRecords/<tool>` and every `npm` is `@reneturcios/<tool>` (one GHCR-only, `npm: null`). Data only; prodforge fetches none of it.
- **The fleet-install question (explicitly judged):** prodforge does **not** download packages, fetch package metadata/tarballs, run `npm install`, or execute anything it downloads — because it downloads nothing.
  - `src/catalog.ts` `mcpConfigFor()` only *generates* config text: `{ command: "npx", args: ["-y", <npm pkg>, "mcp"] }` per MCP tool. `prodforge connect` prints it or writes it to a user-named `--write` path (`src/cli.ts`); the MCP `connect_config` tool returns it as text. **Downstream caveat:** if the user loads that generated config into an MCP client, the *client* will `npx -y` download and run those fleet packages (including any install scripts they carry). That is prodforge's stated fleet-wiring purpose, executed by the client at the user's direction — it is not behaviour of prodforge itself, and each fleet package needs its own audit (the other batches).
  - `prodforge ship` executes only **already-installed local binaries** (see below); absent tools are reported `ABSENT`, never fetched.
- **Code execution — fixed local invocations, no shell:**
  - `src/ship.ts` `runGate()`: `spawnSync(gate.bin, gate.args, { cwd, timeout: 60000, env: { ...process.env, PATH: pathValue } })` — gate bins/args are a hardcoded table of read-only fleet checks (`agentsfile check .`, `envdoc check .`, `mcpvet vet .`, `actionpin audit .`, `flowcheck audit .`, `depguard check .`, `shipcheck check <owner/repo>`); bins not on PATH are skipped as ABSENT. Note: children inherit the **full `process.env`** (standard spawn inheritance) — the fleet tools it runs receive the user's environment.
  - `src/ship.ts` `resolveShipcheckSlug()`: `spawnSync("git", ["config", "--get", "remote.origin.url"], …)` — reads the local git remote to derive `owner/repo`; no network.
  - `src/doctor.ts` `run()`: `execSync` of fixed literal strings only — `node --version`, `npm --version`, `git --version`, `docker --version`, `git rev-parse --is-inside-work-tree`. No user input is interpolated. Doctor checks only the *existence* of `.env.example` / `.env.sample`; it never reads a real `.env`.
- **Env access:** `process.env.PATH` (`src/ship.ts`), plus the env inheritance above. The generated saas-web scaffold template contains `process.env.PORT` — that is code *generated for the user's new project*, not prodforge reading env. No credential stores, no `~/.ssh` / `~/.aws` / Keychain access.
- **Filesystem writes:** `prodforge init <stack> <name> [--dir]` writes template scaffold files into the user-supplied dir and refuses a non-empty directory (`src/scaffolds.ts` `initStack()`); `connect --write <path>` writes the merged MCP config to the user-named path. Nothing else.
- **Examples:** `examples/taskboard/src/index.ts` is an example app that runs a local `node:http` server on `process.env.PORT ?? 3000` (example code, binds locally); `examples/notes` produced no flagged patterns. Tests spawn `tsx` and fake PATH binaries in temp dirs (`test/ship.test.ts` writes `#!/bin/sh` fakes as fixtures) — test-only.
- **Metadata / CI:** `server.json` carries the usual `registry.npmjs.org` / `ghcr.io` / `github.com` manifest strings (never fetched by the tool). `Dockerfile` is a plain `node:20-alpine` build (`npm ci`, `npm run build`, `CMD node dist/cli.js mcp`). Workflows are the fleet template: `registry-publish.yml:17` CI-only `curl` of the official mcp-publisher v1.8.1 tarball; `publish.yml` uses `secrets.NPM_TOKEN` in CI.
- **Obfuscation / data collection:** None. Plain readable TypeScript; no telemetry/analytics.

## Verdict: CLEAN-WITH-NOTES

Notes: (1) `ship` **executes locally installed fleet tools** with fixed read-only argument lists and full env inheritance — its release-gate job; (2) `connect` **generates an `npx -y` MCP config** for the whole fleet — prodforge itself performs **zero network egress and runs no install scripts**, but a client using that config will download and run the named `@reneturcios/*` packages, so those packages stand or fall on their own audits. No hardcoded third-party endpoints, no credential access, no install hooks in prodforge itself.

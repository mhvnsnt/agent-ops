    TorBox API Auth — Lane 1, Round 2 (2026-10-20)¶

    Scope: Root-cause the BAD_TOKEN / 401 failures against ground truth (account fmmg.mars@gmail.com, torrent 119449922 "Documents.zip", infohash 856d01039553693d51c2a98523ca2c9829e8bb63). Supersedes the auth conclusions of TORBOX-RESEARCH-2026-10-19.md (Round 1) where they conflict — Round 1's central assumption (the key is dead / plan is the problem) is disproven by live tests below. No real API key appears anywhere in this file; all authenticated tests ran through the Secure Vault surrogate flow per custom.torbox/CONNECTOR.md.

    VERDICT — root cause is a three-layer placement mismatch, not a dead key¶

    1. The vault-stored TorBox token is VALID right now. Proven 2026-10-20 15:58 UTC: GET /v1/api/torrents/requestdl?torrent_id=119449922&token=<surrogate> → HTTP 200, and the returned CDN link serves byte ranges of the actual 350 GB zip (see §4). The "stale/revoked vault entry" hypothesis is dead.
    2. The vault credential is registered with placement {"query_param": "token"} — Sentinel/authd only substitutes the hsurr: surrogate in that one spot. Put the surrogate in an Authorization: Bearer header and the literal surrogate string reaches TorBox, which correctly answers 403 {"error":"BAD_TOKEN"}. Every Bearer failure through our tooling is explained by this alone.
    3. Most TorBox endpoints accept ONLY Bearer auth. The live OpenAPI spec marks them OAuth2PasswordBearer; sending the (valid) token as ?token= to them returns a raw FastAPI 401 {"detail":"Not authenticated"} — the query parameter is ignored entirely. Only a small set of endpoints (requestdl, notifications/rss, stream/getstreamdata, usenet/webdl requestdl) take ?token= at all. So our helpers fail in both directions:
    4. tb_mylist.py / tb_export.py send ?token= to Bearer-only endpoints → 401.
    5. Anything sending Bearer via the vault sends an unsubstituted surrogate → 403 BAD_TOKEN.

    Net: the API, the account, and the stored key all work. Our connector's auth plumbing is what's broken. The one endpoint family the 350 GB job actually needs (requestdl + CDN range reads) works today, unchanged — see §4.

    1. Live API documentation (fetched 2026-10-20 15:39–15:47 UTC)¶

    • Swagger UI: https://api.torbox.app/docs (FastAPI).
    • OpenAPI spec (public, no auth): https://api.torbox.app/openapi.json → HTTP 200, 96,620 bytes, OpenAPI 3.1.0, title "TorBox API", version 1.0.0, server https://api.torbox.app. (Probed /v1/openapi.json, /v1/api/openapi.json, /docs/openapi.json → all 404.)
    • Human docs: https://api-docs.torbox.app/ — states auth as AUTHORIZATION Bearer {{api_key}}; rate limits are now per API token, 300/min ("We no longer accept IP whitelisting requests due to rate limiting being API token based, rather than IP based"); error table confirms BAD_TOKEN = "The provided token is invalid", NO_AUTH, AUTH_ERROR, OAUTH_VERIFICATION_ERROR, DOWNLOAD_TOO_LARGE (Free 10 GB / Essential 200 GB / Standard 200 GB / Pro 500 GB byte limits as documented).
    • Only security scheme in the spec: OAuth2PasswordBearer (oauth2 password flow, tokenUrl token). No API-key header scheme, no cookie scheme.

    3. Token taxonomy — is there a separate integration token?¶

    No separate "integration token" exists. Distinct credential types found:

    Credential Used for Source
    API key / API token (one per account) Bearer on B-endpoints; ?token= on Q-endpoints; embedded in generated download URLs; WebDAV password (v9) Settings page / refreshtoken
    Web session token ONLY sensitive ops: POST /v1/api/user/refreshtoken body {"session_token": …} ("Gives the user a new API token. Requires the user's session token from the website due to security concerns") and deleteme Website login session
    OAuth tokens (third-party apps/vendors) OAuth2PasswordBearer scheme, tokenUrl token; TorBox.NET documents AccessTokenExpired/RefreshTokenAsync as OAuth2-only — API-key failures surface as plain BAD_TOKEN OAuth flow / vendors endpoints
    Device-code grant GET /v1/api/user/auth/device/start (public) returns device_code, 6-digit code, verification_url (https://torbox.app/oauth/device), interval, expires_in: 600; POST …/auth/device/token then "Returns the user's token once the device code is authorized" — i.e. it hands over the same API token after web authorization. Added in changelog v8 (2025-09-03); free users enabled v8.2.1 (2025-12-20). Verified live today (§4 H). API + website approval
    Presigned download token CDN URLs are …/dld/<presigned>?token=<api_token> (pattern documented since changelog v3.5); valid ~1 hour per old changelog note requestdl response
    Integration OAuth links (Discord/Google Drive/etc.) Link third-party accounts TO TorBox; authorized by the API token, they don't replace it /integration/oauth/*

    Revocation semantics ("Get New API Key"): No public doc, issue, or changelog entry states the semantics explicitly (searched web + GitHub clients 2026-10-20; results were noise from the unrelated torbox.ch project). Indirect evidence for a single-token model: the token is singular everywhere ("your API key" in settings since v3.0; one refreshtoken operation that "gives the user a new API token" gated by the web session token; rate limits keyed per token). Under that model, generating a new key replaces the old one server-side. But it cannot explain our failures: the token currently in the vault — registered before/during the click spree — still authenticates today (§4). Whatever the dashboard clicks did, the vault's token is the account's currently accepted token (or an accepted one). Do not build plans on "the vault key was revoked" — it was not, as of 2026-10-20 16:13 UTC.

    7. Helper / doc defects found (independent of the key)¶

    1. bin/tb_mylist.py + bin/tb_export.py: architecturally incapable of working — they attach the credential as ?token= to Bearer-only endpoints (spec §1). Their 401s were never evidence about the key.
    2. bin/torbox_add_magnet.py: crashes with NameError (verified live 2026-10-20): calls url_with_surrogate_query_param, which is never imported (it imports add_surrogate_to_request instead). Also moot for auth — createtorrent is Bearer-only, so even fixed, it needs Bearer placement.
    3. custom.torbox/CONNECTOR.md is stale: claims bearer_header placement ("so requestdl cannot be called through the surrogate", "tb_reqdl.py is broken"). Reality is the exact inverse: placement is query_param: token, and the requestdl-style helper is the one that works.
    4. bin/tb_reqdl.py prints the raw requestdl JSON — the returned CDN URL embeds the real API token (see §3, presigned-URL pattern). Anyone running it as-is sprays the key into logs. It must redact token= before printing. (This lane's probes redacted in-process and never printed a full link.)

    8. What this unblocks / recommended shape for the parent lane¶

    • The 350 GB extraction can proceed NOW with zero credential changes: requestdl via the existing vault ?token= flow (tb_reqdl pattern, with the §7.4 redaction fix) → CDN link → tail-range reads for the ZIP central directory (72,369-file manifest) → targeted range extraction. All proven live in §4 D/J. mylist/exportdata are not needed for this pipeline.
    • If Bearer-only endpoints are ever needed (mylist, exportdata, createtorrent, user/me, integrations): the credential must exist in the vault with bearer_header placement — placement is per-registration, so the clean shape is a second vault entry for the same key with bearer placement, leaving the working query_param entry untouched. That's a vault re-registration decision for the parent (agent-side flow), not an owner task.
    • Alternative token source if the vault key ever does die: the device-code flow (§3) is live and public — a browser lane with the standing TorBox sign-in can authorize https://torbox.app/oauth/device and the API hands back the account's current token. No dashboard key-copying involved.
    • Do not chase: plan changes for auth reasons (auth is not plan-gated and the documented download-size limit did not fire on the needed path), key regeneration (the current token works; regenerating would only risk invalidating the working vault entry), or proxy bypasses (proxy is exonerated).

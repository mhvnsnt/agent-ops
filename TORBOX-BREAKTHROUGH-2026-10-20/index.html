    TorBox Breakthrough Program — Final Report (2026-10-20)¶

    Owner order: deep research, all agents on it, find a FREE way to pull the 350GB TorBox file with zero manual phone homework, wire up industry-standard/open-source tooling, and actually finish the pull.

    Headline: THE PATH WAS NEVER BLOCKED. The TorBox API key in the Secure Vault is valid and works TODAY. The "BAD_TOKEN" saga was our own connector plumbing: the vault credential is registered with query_param: token placement, so the surrogate is only substituted in a ?token= query parameter. Every Bearer-header call sent the literal hsurr: surrogate to TorBox (correctly rejected as BAD_TOKEN), and every ?token= call to Bearer-only endpoints was ignored (401). The one endpoint family the pull actually needs — requestdl + CDN range reads — works right now, unchanged, on the existing Essential plan. No upgrade, no new key, no owner action.

    Lane reports: torbox-lane1-auth.md, torbox-lane2-debrid-live.md, torbox-lane3-alternatives.md, torbox-lane4-compute.md, torbox-lane5-agents.md (+ torbox-lane5-agents/ verbatim outputs), torbox-lane6-oss.md, torbox-lane7-seedbox.md.     A1. BAD_TOKEN: community reports, key revocation, OAuth/integration tokens, full endpoint groups¶

    • Community/GitHub-issue reports (2025–2026): Lane 1 searched the web and GitHub clients for BAD_TOKEN causes/fixes on 2026-10-20 — results were noise (an unrelated torbox.ch project); no public issue documents this failure mode or a fix. Lane 6 surveyed 342 TorBox-related GitHub repos (official torbox-media-center 284★, atba 180★, DebriDav 155★, DebridDownloader 94★, magnetar 90★, AIOStreams 2,930★, comet 1,120★): every client authenticates with the same single API key; none documents a BAD_TOKEN workaround. The cause in OUR case is proven locally (placement mismatch, §1), not community-sourced: garbage-token control → 403; vault token via ?token= → 200, repeatedly. No TorBox-side auth change exists to blame: official changelog's latest entry is v9.2 (2026-08-17); status page shows no October auth incident (Lane 1 §6).
    • Does generating a new key revoke the old one? No public doc, issue, or changelog entry states the semantics (searched). Indirect evidence supports a single-token model (one refreshtoken operation, rate limits keyed per token, "your API key" singular in settings since v3.0) — under that model a new key replaces the old server-side. BUT it cannot explain our failures: the token in the vault still authenticates today (Lane 1 §3–§4), so whatever the dashboard clicks did, they did not leave us with a dead key. Operational rule from this program: never regenerate the key as a diagnostic — it risks invalidating the one working credential.
    • OAuth / separate integration token? There is NO separate integration token. Token taxonomy (Lane 1 §3, from the live OpenAPI spec + docs): (1) the single API token (Bearer on most endpoints, ?token= on requestdl/rss/ getstreamdata); (2) a web session_token used ONLY to authorize POST /user/refreshtoken and deleteme; (3) OAuth2PasswordBearer is the spec's only security scheme — vendor/third-party apps get OAuth tokens, and TorBox.NET documents refresh as OAuth-only while API-key failures surface as plain BAD_TOKEN; (4) a live device-code flow (GET /v1/api/user/auth/device/start, public, verified 200 today) returns the SAME API token after web authorization — a fallback source, not a distinct credential; (5) presigned CDN tokens embedded in download URLs (~1h per old changelog note).
    • Full endpoint groups (live spec https://api.torbox.app/openapi.json, HTTP 200, 87 paths, fetched again 2026-10-20 by the coordinator): general (stats, changelogs, speedtest, notifications incl. rss Q), user (me, stats, subscriptions, transactions, referral, settings, refreshtoken, deleteme, auth/device/), torrents (createtorrent, asynccreatetorrent, controltorrent, controlqueued, edittorrent, mylist, exportdata, getqueued, checkcached, magnettofile, torrentinfo, requestdl Q), usenet (create/control/edit/mylist/checkcached/provider/, requestdl Q), webdl (create/control/edit/mylist/checkcached/hosters, requestdl Q), queued (GET /v1/api/queued/getqueued, POST /v1/api/queued/controlqueued
    • the torrents/ duplicates), rss (addrss/controlrss/modifyrss/getfeeds/getfeeditems), stream (createstream, getstreamdata Q), integration (cloud-upload jobs — see A2; oauth link/callback/register/ unregister/me; discord linked_roles), vendors (account CRUD).     A2. TorBox server-side cloud transfer (Drive/Dropbox/OneDrive)¶

    Yes — it exists, as API "integration" jobs (verified from the live OpenAPI spec by the coordinator, 2026-10-20): POST /v1/api/integration/googledrive, /dropbox, /onedrive, /gofile, /pixeldrain, /1fichier; job management GET /integration/jobs, GET /integration/job/{job_id}, GET /integration/jobs/{hash}, DELETE /integration/job/{job_id}. Request shape (spec schemas): for Google Drive, AddToGoogleDrive requires {id (torrent id), google_token} with optional file_id, zip, type (Dropbox identical with dropbox_token) — i.e., you first link the destination cloud via the /integration/oauth/{provider} flow, then TorBox's servers push the downloaded item into it. Limits: the spec states no per-job size limit for integration transfers (the documented DOWNLOAD_TOO_LARGE table governs requestdl, §1); destination quotas govern in practice — free Google Drive is 15GB (owner-established), so Drive is a non-target for a 350GB file regardless. Usability for us: blocked today — every integration endpoint is Bearer-only, and our vault credential substitutes only at query_param placement (§1). Unblocking = the second vault entry with bearer_header placement (parent/vault action, §1 fix #4) plus an OAuth link of the destination cloud (browser lane). The web UI exposes the same feature as "Send to cloud" integrations per the API structure; the dashboard route itself was not browser-verified (parent notes the browser lane is down), so the API evidence above is the verified layer and the UI claim is labeled unverified.

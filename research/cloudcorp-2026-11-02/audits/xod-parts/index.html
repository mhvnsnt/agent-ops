    Audit — Xod parts (scoped extraction candidates only)¶

    • Repo: github.com/CloudCorpRecords/xod (MIT). The rest of the Xod app is OUT of scope (already decided: not adopting the app) and was not audited, except where an in-scope file delegates into it — those delegation points are named below.
    • Release version: 0.9.23 — app/version.py: VERSION = "0.9.23"; latest GitHub release v0.9.23 (published 2026-11-02).
    • Git HEAD (main): 6e5ebd4a0113bcf68800b6e034aa3d88e9b1f877 (2026-11-02T11:19:25Z), via gh api repos/CloudCorpRecords/xod/commits/main.
    • Method: git clone is broken VM-wide (unable to write symref for HEAD: Operation not permitted) and codeload tarballs return 0 bytes through the proxy, so the re-clone into src/xod/ could not be completed by clone/tarball. Primary method used: gh api repos/CloudCorpRecords/xod/contents/<path> (base64 content, decoded) and gh api repos/CloudCorpRecords/xod/git/trees/main?recursive=1 for file listings — slow (~10s/call) but reliable. Key evidence was re-verified through this route after the coordinator's environment update and matches exactly (sentinel.py stdlib-only imports and the llm_service delegation at :256/:265; agent_clis.py UNSAFE_FLAGS at :75, _safe_extra enforcement at :235/:469/:489, create_subprocess_shell install path at :867/:881). Supplementary full-file reads via raw.githubusercontent.com gave identical content/line numbers. Only src/xod/app/version.py (110 bytes) is persisted under src/; treat the per-file reads below as the audit record.
    • Files audited: app/services/sentinel.py (full, 316 lines), tests/smoke/run_sentinel_test.py, scripts/benchmark.py, app/services/scorecard.py (full), app/services/worktrees.py (full), app/services/agent_clis.py (1,105 lines / 60 KB — registry, env, run/session/install/login paths read in context), app/services/harness.py (853 lines — ONLY the crew_start / seat-record surface: tool manifest entries, invoke() dispatch, crew_read field whitelist, plus its _authorize gate).

    1. app/services/sentinel.py — CLEAN-WITH-NOTES¶

    • Direct egress: NONE — verified. Top-level imports are stdlib only (contextvars, json, logging, re, time, uuid, typing). No urllib/requests/httpx/socket/subprocess, no os.environ/getenv, no eval/exec, no file opens/writes anywhere in the file. The core review() is pure regex classification over in-memory turn state; decisions are kept in an in-memory LOG list capped at 100 entries.
    • curl|sh patterns are detection DATA — confirmed, not malicious: _REMOTE_RUN_RE matches curl|wget|iwr|irm … | sh|bash|iex|python in candidate actions so they get held; _SECRET_RES, _INJECTION_RE, _SAFE_DOMAINS are likewise detector patterns. The module's purpose is holding actions for an approval card.
    • Note 1 — delegated LLM egress in review_message(): this one async function lazy-imports app.services.llm and calls llm_service.chat_completion(..., task="sentinel") with the user's asked text (last 2,000 chars), the pending action's args (2,000 chars) and up to 3,000 chars of untrusted content, asking whether the action follows the person or the page. So sentinel.py itself opens no connection, but adopting review_message means that content goes to whatever LLM provider the host app has configured (the out-of-scope llm_service). Failures are fail-open for this check only (exception → returns None; the regex rules still applied). Extract review()/page_orders() alone and there is zero egress; extract review_message() and you inherit the host's LLM egress.
    • Note 2 — hold() side effects are internal: lazy-imports app.services.mcp_client (mcp_hub.pending[...], in-memory approval queue) and app.services.agent_log; _taildrop_ask_first() lazy-imports app.services.taildrop to read a setting. No network/file activity in sentinel.py itself at these points.

    2. tests/smoke/run_sentinel_test.py — CLEAN (test only)¶

    • Sets os.environ only to isolate itself: XOD_SPEECH=off (line 17, "tests never reach the speakers") and XOD_DATA_DIR = a fresh temp dir (line 20). All writes are under that temp dir (ran.txt, Receipts/, keep/).
    • The curl … | sh / iwr … | iex strings at lines 84–87 and the tracker/shady-example URLs are test vectors asserting sentinel holds them (and one asserting the exact user-given command is not held). Example API-key strings are fixtures for the secret rule.
    • It stubs the model: llm_mod.llm_service.chat_completion is replaced with a fake returning scripted verdicts (and restored), capabilities._chat_model and worker.llm_service.deliberate_stream are faked — the test makes no real LLM/web calls of its own. It does execute one real tool flow (computer_run_command) but only after simulating approval, inside the temp dir.

    3. scripts/benchmark.py — CLEAN-WITH-NOTES (dev script)¶

    • Egress: its own HTTP is only to the server it spawns: binds a free port on 127.0.0.1, launches uvicorn app.main:app --host 127.0.0.1 via subprocess.Popen (arg list, no shell), polls http://127.0.0.1:{port}/ and POSTs benchmark cases to /api/chat. One check fetches a page from 127.0.0.1:{http_port} it had the agent under test serve. No external hosts in the script.
    • Env: reads LLM_MODEL / LLM_PROVIDER / LLM_BASE_URL (defaults qwen2.5:14b / ollama / http://localhost:11434/v1) and passes the full os.environ plus overrides (XOD_DATA_DIR, XOD_FILES_HOME → temp dirs, XOD_AUTOCONNECT=0, LLM_*) to the spawned server. Consequence by design: benchmark chat content goes to the operator-chosen LLM provider — local Ollama by default, external only if the operator points --base-url/--provider there. (One built-in case, "a live answer" — Tokyo weather — makes the app under test use the web; that is the app, not this script.)
    • Shell note: helper runs(cmd) uses subprocess.run(..., shell=isinstance(cmd, str)). Its only string-form call site is the hardcoded "node index.js" check inside the temp work dir (running the project the benchmarked agent just built there, to verify it). All other call sites pass arg lists. Acceptable for a dev benchmark harness; not a remote-input surface.
    • fs writes: everything case-related lives in tempfile.mkdtemp dirs (work dir removed at the end via shutil.rmtree(W)); it creates a throwaway venv there. Persistent writes are only the results files it exists to produce: docs/reliability.json and docs/RELIABILITY.md in the repo (paths scrubbed of user names/home paths first, scrub()).

    4. app/services/scorecard.py — CLEAN¶

    • Read-only aggregation. No imports beyond json, time, typing; no env, no network, no subprocess, no file opens, no writes in this file.
    • It reads (a) the local recorded-events DB via dataset_recorder._conn() with parameterised SELECT-only queries over turns and llm_calls tables, (b) crew job state in memory (crew._load(), crew._jobs), (c) eval suite results via app.services.evals. Its own header is accurate: "Nothing new is recorded for it." (The recording of turns/LLM calls happens in those other services — out of scope here; scorecard itself collects nothing and sends nothing anywhere.)

    5. app/services/worktrees.py — CLEAN-WITH-NOTES¶

    • Execution: git is only ever run as subprocess.run([git, *args], …, stdin=DEVNULL) — arg arrays, no shell, no string commands (_git(), lines 41–46). Same for the gh call below.
    • Env: _env() inherits the process environment (via agent_clis._env() if importable, else dict(os.environ)) and adds GIT_TERMINAL_PROMPT=0, GIT_EDITOR=true (never block on a credential prompt/editor). Env is passed to git/gh subprocesses — normal for git operations on the user's own repos.
    • fs writes — where: creates worktrees under DATA_DIR/worktrees/ (ROOT), branch xod/<name>; commits the job's changes there, merges locally, or removes the worktree/branch. That is the file's stated job.
    • Note — commit uses --no-verify: _commit() runs git commit -q --no-verify, i.e. repo git hooks are skipped for these automated job commits. Deliberate in code, worth knowing before adopting.
    • Note — the one egress path: pull_request() runs git push -u origin <branch> and then gh pr create --head … --title … --body … (arg array). That sends the branch + PR title/body to the repo's configured origin (the user's GitHub) — only when pull_request() is explicitly invoked; it refuses if there is no origin remote. No other network activity; merge/changes/remove are purely local git.

    6. app/services/agent_clis.py — CLEAN-WITH-NOTES (strong notes on install())¶

    • The --yolo refusal is REAL in code — verified: UNSAFE_FLAGS regex (lines 75–76) covers --dangerously…, --yolo, --yes-always, --full-auto, --bypass…, --no-sandbox, --skip-permissions, --allow-all, -y, --auto-approve, --trust-all. _safe_extra() (lines 208–214) raises CliError if any supplied extra arg matches, and it is enforced on every agent-launch path found: headless run() (line 235: args = […run template…] + _safe_extra(extra)), generic-program sessions via _program_argv() (line 469, when the program is a known agent binary), and session_start() (line 489). The headless run templates themselves (claude -p, muse exec, codex exec, gemini -p, …) contain no unsafe flags. Prompts are substituted into a single argv element, not parsed as flags.
    • Spawning is its job and is arg-array based: run() uses asyncio.create_subprocess_exec(path, *args, …); sessions use subprocess.Popen(argv, …) (PTY). One exception is install() (below) and search_path() running the user's login shell as [shell, "-lic", "printf %s \"$PATH\""] — a fixed literal string, no injected input.
    • Credential handling — presence only, verified: for each agent, signed_in file paths (e.g. ~/.claude/.credentials.json, ~/.codex/auth.json) are checked with .exists() only — the header comment "only whether the file exists is checked; it's never read" matches the code (signed_in(), lines 164–173). key_env names (META_API_KEY, ANTHROPIC_API_KEY, OPENAI_API_KEY, GEMINI_API_KEY, CURSOR_API_KEY, AMP_API_KEY) are checked with os.environ.get(...) for truthiness only; values are never read out, logged, or sent by this file. login() runs the agent's own login command and opens its auth URL in the browser (Popen(["open"|"explorer", url]), line 768) — Xod never handles a password.
    • Env note: _env() (line 128) passes a copy of the full os.environ (with PATH/TERM adjustments) to spawned agent CLIs. That is how those agents get their own API keys — by design — but it means any key in Xod's environment is visible to any agent it launches.
    • STRONG NOTE — install() is a real curl|sh execution path: the AGENTS registry hardcodes vendor install commands, three of them remote-script pipes — Muse: curl -fsSL https://muse.meta.ai/install.sh | bash; Claude Code: curl -fsSL https://claude.ai/install.sh | bash (Windows: irm https://claude.ai/install.ps1 | iex); Cursor: curl https://cursor.com/install -fsS | bash — others are npm install -g … / brew install … / pip-based. install() (lines ~867–895) executes the string via asyncio.create_subprocess_shell(...) in $HOME with the full env. Mitigations in evidence: the commands are hardcoded vendor-published installers (not user/remote-supplied, not configurable), and install()'s docstring states it runs "Only after the person's OK (the tool holds it as an approval card first)" — but that gate lives in the calling tool layer (out of scope), not inside install() itself. If this file is extracted, either drop install() or keep an equivalent approval gate in front of it.
    • Other egress: none from this file directly; the agents it launches make their own provider calls once running (their job). find() also returns each agent's install string as data to the UI.

    7. app/services/harness.py — crew_start / seat-record surface only — CLEAN-WITH-NOTES¶

    • The audited surface: the tool manifest entries (crew_start, kind "write", lines 484–487; crew_status/crew_read descriptions referencing the seat record, lines 489–490, 512–513), the invoke() dispatch for crew_start (lines 772–784), and the seat pass-through in _tool_crew_read (line 655 whitelists "seat" among the returned job fields; line 844 puts out.get("seat") in the envelope's verified block).
    • What it does: crew_start validates a non-empty task, then delegates verbatim to crew.start(task, folder, agent, kind) — with kind="board" requesting a board seat. The seat record itself (model requested / model that actually ran / how that is known) is created inside app.services.crew — out of scope; in harness.py the seat is opaque data that is only carried in and read back out. Within this surface there is no subprocess, no env access, no direct network code, and no file I/O in harness.py.
    • Gate — verified in code: every invoke() call runs _authorize() first (lines 208–228): (1) the beacon's Tailscale whois must say the caller IP is a device on the same account (same_account, else 403), and (2) the caller must present the harness_token setting in the X-Harness-Token header, compared with hmac.compare_digest (401 on mismatch; 503 — port closed — when no token is configured; a configured canary token presentation is logged as a security event and rejected). Work submitted still goes through the app's normal approval-card path; the harness adds no bypass.
    • Out-of-surface warning (same file, NOT audited in depth and NOT part of the seat surface): harness.py as a whole also contains a family-relay tier — _relay() uses httpx to call http://{member-endpoint}:{BEACON_PORT}/… on other family machines' Xod beacons, and task records are persisted to DATA_DIR/harness_tasks.json (capped at 100). Extracting only the crew_start/seat code does not bring these; importing the whole file would. Adopt the surface, not the file.

    Overall verdict for the Xod parts: CLEAN-WITH-NOTES¶

    No file in scope contains telemetry, obfuscation, credential exfiltration, or covert egress. The notes that matter for adoption: sentinel's review_message() delegates content to the host's configured LLM; agent_clis' install() executes hardcoded vendor curl|sh installers through a shell and relies on a caller-side approval gate; worktrees' pull_request() pushes to the user's origin and its commits skip git hooks (--no-verify); benchmark is a localhost-only dev harness whose spawned server talks to the operator-chosen LLM provider.

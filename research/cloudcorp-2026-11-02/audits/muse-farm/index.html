    Security Audit — muse-farm¶

    • Repo: github.com/CloudCorpRecords/muse-farm (MIT)
    • Version: 0.5.1 (farm.py:23 __version__ = "0.5.1")
    • Packaging / bin: None. No pyproject.toml, setup.py, package.json, or console entry point — the entire tool is one stdlib-only Python file, farm.py (57,594 bytes), invoked as python3 farm.py <run|batch|schedule|init|supervise|think|adopt|status|self-update>. Python 3.9+, zero third-party dependencies (imports: argparse, concurrent.futures, json, os, re, shlex, subprocess, sys, time, datetime; urllib.request imported lazily in two functions).
    • Method used: git clone is broken VM-wide (“unable to write symref for HEAD: Operation not permitted”) and codeload tarballs return 0 bytes through the proxy, and tar extraction into the scratch tree hit write-EPERM — so no local src/ copy could be persisted. Primary method per coordinator: gh api repos/CloudCorpRecords/muse-farm/git/trees/main?recursive=1 for the file inventory and gh api repos/CloudCorpRecords/muse-farm/contents/<path> (base64 content) for source, cross-checked with streamed raw.githubusercontent.com reads: full read of all of farm.py in four chunks, plus grep -n scans of the files listed under Coverage. Nothing was installed or run.
    • Coverage: Complete — this repo has only 8 files and all were covered: farm.py (the entire tool, read in full), tests/test_farm.py, jobs.example.json, supervise.example.json, README.md, CHANGELOG.md, LICENSE, .gitignore. There is no src/ dir, no package.json/pyproject.toml, and no .github/ workflows in this repo.

    Findings¶

    • Install hooks: None possible — there is no packaging metadata at all. Nothing runs on download/clone.
    • Core execution (its job, as expected): build_exec_cmd() builds an argv list [muse, exec, …flags…, prompt]; cmd_run / cmd_batch run it with subprocess.run(cmd) in argv form. Grep confirms no shell=True anywhere, no eval/exec() of strings, no os.system. --yolo and --trust-workspace are passed through only when the user sets them (CLI flag or jobs-file entry). batch reads a user-supplied jobs JSON and writes one log per job under the runs dir. init runs [muse, init] in the user-named workspace and writes an AGENTS.md stub there if absent.
    • Scheduling / persistence (opt-in): schedule only prints cron/launchd entries by default. With explicit --install it writes a plist to ~/Library/LaunchAgents (farm.py:302) and runs launchctl bootstrap gui/<uid> <plist>. The baked-in scheduled PATH is ~/.local/bin + system dirs (farm.py:210).
    • supervise / adopt — local access BEYOND spawning muse exec (flagged per audit brief):
    • Reads the user's Muse session data under SESSIONS_ROOT = ~/.local/share/muse/sessions (farm.py:359): session-log (session.jsonl) tails (128 KB default, widening up to the whole file in _scan_mission) to reconstruct each session's mission from runtime.user_intent.accepted text (_mission_from_records), and session tool-outputs/ files (up to 300 files × 32 KB, _collect_mention_text) to infer the session's workspace from path mentions (_inferred_workspace).
    • Inspects processes: ps -eo pid=,args= + lsof to map live muse-bin PIDs → sessions and their working directories (_live_session_pids, _session_cwds, _ps_usage).
    • Acts on stalls by sending nudges via muse session-message send (_send_nudge) and, when the supervise config provides workspace+mission, spawning headless continuations (_continue_exec: muse exec with trust_workspace forced True, yolo from per-session config, capped by max_continues_per_day, default 6). It never kills a process — grep confirms no os.kill / signal use.
    • Writes only supervisor bookkeeping in --state-dir (default <farm>/runs/supervise): state.json, status.json, supervisor.log, continue-<uuid>-<ts>.log.
    • All of the above stays on the local machine except through the two opt-in channels below.
    • Network egress — only two paths, both user-configured:
    • ntfy notifications. _ntfy() (farm.py:547-551) POSTs via urllib.request to {url}/{topic}. Default URL is hardcoded https://ntfy.sh (farm.py:966, overridable in config); the topic has no default — it comes only from --ntfy-topic or the user's supervise config, so no ntfy call happens without user configuration. Bodies sent are minimal metadata only: session <uuid-prefix> is gone and session <uuid-prefix> idle <age> (stall #n), with a Title header. No mission text, no log content, no credentials.
    • think --backend api. _think_via_api() (farm.py:872-880) POSTs {api_base}/chat/completions (OpenAI-compatible) via urllib.request. api_base is user-supplied (config/CLI; the README's https://api.fireworks.ai/inference/v1 is a documentation example only). In supervise mode the prompt sent to that endpoint can include the session's mission text, its done_when, and continuation-log excerpts (≤1,500 chars in the verdict prompt) — i.e. local session-derived content leaves the machine only to the endpoint the user configured. The default think backend is muse (via muse exec, no API call).
    • Credential / env access: Exactly one read: farm.py:869 os.environ.get(key_env) in _think_via_api, where key_env is the name of an env var chosen by the user, defaulting to MUSE_FARM_API_KEY (farm.py:897, :1351); the key is sent as Authorization: Bearer … only to the user-configured api_base. (Deliberate design: --api-key-env help says “never pass the key itself”.) No other os.environ access; no ~/.ssh, ~/.aws, Keychain, or browser-profile access.
    • Self-update (user-invoked remote-code path): cmd_self_update refuses non-git checkouts and dirty trees, then runs git pull --ff-only in the farm checkout (farm.py:1267) and executes the pulled tree's test suite (python -m unittest discover -s tests). This downloads new code from the checkout's git remote and runs part of it — only when the user explicitly runs farm.py self-update. There is no auto-update on any other path.
    • Obfuscation / data collection: None. One plain, heavily commented Python file; no telemetry/analytics; the only hardcoded third-party host is the ntfy.sh default above (plus the Apple plist DTD string at farm.py:224, a template literal that is never fetched).

    Verdict: CLEAN-WITH-NOTES¶

    Nothing malicious or covert: no shell execution, no process killing, no credential stores, no author telemetry, and every network destination is user-configured except the ntfy.sh default host. The notes that must travel with any install decision are the breadth of its local remit, all of it the documented supervisor job but beyond “wraps muse exec”: it reads Muse session logs and tool-output files under ~/.local/share/muse/sessions, inspects ps/lsof, can install launchd persistence (schedule --install), can send stall metadata to ntfy.sh once the user sets a topic, can send mission/log-derived prompts to a user-configured OpenAI-compatible API with a key from MUSE_FARM_API_KEY (or a user-named env var), passes through --yolo / --trust-workspace, and its self-update pulls and test-executes remote code on explicit invocation.
